# 2026-11-03 작업 메모: 전사본 칸 창 크기 · 접근성 계획

> 상태: **조사·제안 메모.** 1~6절은 전사본 칸 창 크기 문제를 코드로만 확인한 내용이고, Windows 실기에서 재현·확인하지 않았다. 7~8절은 접근성과 구조 보강 제안으로, 무엇을 할지는 아직 정하지 않았다. 문서 전체에 고친 코드는 없다.
>
> **넘겨받은 사람에게.** 이 문서는 결정문이 아니라 참고 메모다. 여기의 추천·순서·구조는 한 단계 낮춰 읽고, 시니어 개발자의 직관과 판단을 우선한다. 판단의 출발점은 지금까지 이 저장소에서 해 온 스타일(빌드 도구 없는 바닐라 JS, `app.js`의 구역 주석과 위임 이벤트, Go 바인딩, i18n 카탈로그)이다. 더 나은 방향이 보이면 이 문서를 따르지 않아도 된다.

## 1. 증상

Windows에서 전사본 칸을 **열고 → 닫고 → 다시 열면** 창 크기와 비율이 처음과 달라진다.

- 목록만 있는 창은 480×680으로 시작한다(`app.ListWidth`, `cmd/nalmeok/main.go:201`).
- 칸을 열면 1100 폭으로 넓어진다(`app.PaneWidth`).
- 칸을 닫으면 480이 아니라 **760**으로 돌아온다(`app.PaneMinWidth`).
- 다시 열면 1100이라, 두 번째부터는 1100↔760으로 고정된다.

즉 첫 번째 여닫기에서만 목록 창이 넓어진 채로 남고, 창의 가로세로 비율도 480:680에서 760:680으로 바뀐다.

## 2. 확인한 코드 경로

`internal/app/pane.go`의 `fitWindow`가 창 크기를 직접 바꾼다.

| 순서 | 위치 | 동작 |
|---|---|---|
| 1 | `pane.go:112` | 칸을 열 때 `WindowSetMinSize(PaneMinWidth=760)` |
| 2 | `pane.go:116` | 최대화·전체 화면이면 여기서 끝 |
| 3 | `pane.go:119` | `WindowGetSize`로 **현재 폭**을 읽음 |
| 4 | `pane.go:126` | 그 폭을 `a.listWidth`에 기억 |
| 5 | `pane.go:135` | `WindowSetSize(1100)`으로 넓힘 |
| 6 | `pane.go:143` | 칸을 닫을 때 `a.listWidth`로 되돌림 |

기억해야 하는 값은 **칸을 열기 전의 폭(480)** 인데, 3번이 1번 뒤에 있어서 Windows에서는 이미 늘어난 폭을 읽는다.

## 3. 원인 후보 (실기 확인 전)

Wails v2.17.1에서 `WindowSetMinSize`의 동작이 플랫폼마다 다르다.

- **Windows**: `winc.ControlBase.SetMinSize`가 현재 폭이 새 최소값보다 작으면 그 자리에서 `MoveWindow`로 창을 늘린다. 동기 호출이다.
  - `internal/frontend/desktop/windows/winc/controlbase.go:218-236`
  - 이어서 부르는 `Size()`는 이미 늘어난 760을 돌려준다(`controlbase.go:257-262`).
- **macOS**: 같은 함수가 `dispatch_async`로 메인 스레드에 넘기기만 한다.
  - `internal/frontend/desktop/darwin/Application.m:106-110`, `WailsContext.h:20`
  - 실제 크기 조정은 `WailsContext.m:97-105`, `123-136`에서 나중에 일어나므로, 직후 `WindowGetSize`는 보통 아직 480을 읽는다.

그래서 같은 순서 버그가 Windows에서는 매번, macOS에서는 드물게(경합) 나타난다.

정리하면 원인 후보는 **"최소 크기를 올린 뒤에 현재 폭을 읽는다"** 이다. 기본 목록 창(480)이 칸 최소 폭(760)보다 좁기 때문에 첫 여닫기에서 항상 걸린다.

## 4. 같은 함수에서 함께 본 것

고치기 전에 같이 판단할 것들이다. 둘 다 이번 증상과 원인이 다르다.

1. **이미 넓은 목록 창에서 열면 폭을 잊는다.** 목록 창을 1100 이상으로 늘려 둔 뒤 칸을 열면 `pane.go:122`에서 바로 끝나 `listWidth`를 기록하지 않는다. 닫을 때 `ListWidth`(480)나 옛 값으로 줄어들어 사용자가 맞춰 둔 폭이 사라진다.
2. **화면 밖 보정의 단위가 섞여 있다.** `pane.go:137`은 `WindowGetPosition`(Windows에서 물리 픽셀)과 `screenWidth`/`target`(논리 픽셀)을 더한다. 배율이 100%가 아니면 필요 없이 창을 왼쪽으로 밀 수 있다. Wails의 `Screen`에는 화면 위치가 없어서, 이 보정을 제대로 하려면 다른 방법을 찾아야 한다.

## 5. 고치는 방향 (후보)

확정안이 아니다. "이렇게 하면 될 것 같다" 수준으로 적어 둔다.

### 후보 A: 최소 크기를 올리기 전에 폭을 읽는다

가장 작은 변경이다.

```go
// 최소 크기를 건드리기 전에 읽는다. Windows는 더 좁은 창을 즉시 늘리므로
// 나중에 읽으면 전사본 최소 폭(760)을 목록 폭으로 기억하게 된다.
width, height := wailsruntime.WindowGetSize(ctx)
if open {
    wailsruntime.WindowSetMinSize(ctx, PaneMinWidth, WindowMinTall)
    a.mu.Lock()
    a.listWidth = width
    a.mu.Unlock()
    if width >= PaneWidth {
        return // 넓은 목록 창은 그 폭을 그대로 기억하고 늘리지 않는다
    }
    ...
}
```

- 최대화·전체 화면 판정은 지금처럼 폭을 읽기 전에 둬야 최대화된 크기를 기억하지 않는다.
- 칸을 열 때 이미 1100 이상이면 `listWidth`를 기록하고 끝내면 4-1도 같이 해결된다.
- `SetPane`에서 `a.cfg.Pane()`으로 이전 상태를 먼저 읽고 `open != wasOpen`일 때만 `fitWindow`를 부르면, 중복 호출이 `listWidth`를 1100으로 덮어쓰는 일도 막을 수 있다.

### 후보 B: 최소 크기 변경 순서를 여닫기마다 다르게 한다

- 열 때: `SetSize(1100)`을 먼저 하고 `SetMinSize(760)`을 나중에 하면, 최소값을 올릴 때는 이미 넓어서 즉시 늘어나지 않는다.
- 닫을 때: 반대로 `SetMinSize(420)`을 먼저 해야 `SetSize(480)`이 최소값에 걸리지 않는다.

동작은 하지만 "열 때는 이 순서, 닫을 때는 저 순서"라서 읽는 사람이 이유를 알아야 하는 코드가 된다. 어느 쪽이 나은지는 구현자 판단에 맡긴다. 이 글을 쓴 사람은 A가 더 단순해 보였다.

### 테스트

`fitWindow`는 Wails 런타임을 직접 부르므로 지금 구조로는 단위 테스트가 어렵다. 최소 폭·목표 폭·기억할 폭을 계산하는 순수 함수로 빼면 Windows 없이도 검증할 수 있다. 이건 어디까지나 후보이고, 실제 수정 때 정한다.

## 6. 남은 확인

- [ ] Windows 실기에서 증상 재현. 창 폭을 재거나, `fitWindow`에 임시 로그를 넣어 `WindowSetMinSize` 전후의 `WindowGetSize` 값을 남긴다.
- [ ] 후보 A를 넣었을 때 첫 여닫기 뒤 480으로 돌아오는지 확인.
- [ ] 이미 1100 이상으로 늘린 목록 창에서 열고 닫아도 폭이 유지되는지 확인.
- [ ] Wails 버전을 올리면 Windows·macOS의 `SetMinSize` 동작이 달라질 수 있으니, 올릴 때 이 문서를 다시 본다.

## 7. 접근성 작업 계획 (제안)

> 확정 전 제안이다. "릴리스에 필요한 만큼"의 초안이고, 범위는 7-6의 후보 중에서 정한다. macOS는 Apple HIG의 Accessibility 지침을, Windows는 Microsoft의 접근성 지침을 출발점으로 삼았다. 공통 기준은 WCAG 2.2 AA를 두는 안을 적었다. 항목과 순서 모두 후보이며, 시니어가 다시 고르는 것을 전제한다.

### 7-1. 기준

- **WCAG 2.2 AA**: 본문 대비 4.5:1, 큰 글자·UI 요소·포커스 표시 3:1, 키보드만으로 모든 조작, 200% 확대에서 내용 손실 없음, 색만으로 정보를 전달하지 않음, 이름·역할·상태 노출. 기준을 어디까지 적용할지는 시니어가 정한다.
- **macOS (Apple HIG Accessibility)**: VoiceOver, Full Keyboard Access, Increase Contrast, Reduce Motion, Reduce Transparency, Differentiate Without Color, 표준 메뉴·시트·단축키.
- **Windows**: Narrator(UI Automation), 고대비 테마, 텍스트 크기·DPI 200%, 키보드 규칙(Tab·Shift+F10·F6), 애니메이션 줄이기.
- 앱은 Wails WebView(WKWebView·WebView2)라서 DOM의 시맨틱과 ARIA가 OS 접근성 트리로 그대로 간다. 그래서 작업의 대부분은 `frontend/dist`에서 한다.

지금도 일부는 갖춰져 있다. 시트의 `role=dialog`·`aria-modal`, 전사본 토글의 `aria-pressed`, 무료|유료 탭의 `aria-selected`, 진행 막대의 값, 토스트의 `role=status`, 폼 오류의 `role=alert`, 아이콘 버튼의 i18n `aria-label`, Esc·⌘F·키 목록 Enter/Space가 그것이다. 아래는 그 위에 얹는 목록이다. 표의 우선순위는 제안자의 판단이니 참고만 하고, 시니어가 다시 매기는 것을 전제한다.

### 7-5. 이 앱에서 먼저 할 것 (제안 순서)

아래 순서도 후보일 뿐이다. 큰 구멍 순으로 적었지만, 시니어가 다르게 볼 수 있다.

1. **목록 키보드** (A1·A7): 가장 큰 구멍. 행을 포커스 가능하게 하고 선택·열기·삭제·메뉴를 키로.
2. **전사본 라이브 영역 정리** (A4): `#pane` 전체 `aria-live`를 빼고 상태 한 줄만 알림.
3. **시트 포커스** (A6): 키·도움말·PDF.
4. **대비·포커스 링·모션** (A7·A8·A9): 디자인 토큰과 CSS로 한 번에.
5. **macOS 메뉴·단축키** (M3·M4) / **Windows 고대비·텍스트 크기** (W2·W3).
6. **스크린리더 실기 검증**: VoiceOver·Narrator로 처음부터 끝까지.
7. (선택) 자동 검사: axe-core를 개발자 도구에서 돌리는 체크리스트, 대비 토큰 검사.

### 7-6. 같이 정할 것

- 범위: P0만 릴리스에 넣을지, P1까지 넣을지.
- 전사본 칸을 열 때 포커스를 칸으로 옮길지, 목록에 둘지(목록 탐색 흐름 vs 바로 읽기).
- 단축키 집합: Space 미리보기, Enter 열기, Delete/⌘⌫ 삭제, F6(Windows) 등. 기존 입력과 충돌 검사.
- 상태 알림 정책: 진행률을 매번 읽지 않고 완료·실패·한도 소진만 알린다.
- 실행 취소 4초를 늘릴지, 메뉴에 "실행 취소"를 둘지.
- macOS 표준 메뉴를 Wails 옵션으로 넣을지(App·Edit·Window·Help).
- 검증 환경: macOS 버전, Windows 10/11, 사용할 스크린리더.
- 자동 검사를 CI에 넣을지(WebView UI라 어려움) 아니면 수동 체크리스트로 둘지.

### 7-7. 검증 체크리스트 (초안)

- **macOS**: VoiceOver(⌘F5)로 목록→칸→시트, Full Keyboard Access를 켜고 마우스 없이 전체 동작, Increase Contrast·Reduce Motion·Reduce Transparency를 켜고 확인, 200% 확대.
- **Windows**: Narrator(Ctrl+Win+Enter)로 같은 흐름, 고대비 테마, 텍스트 크기 200%, 배율 150%, 키보드만으로 전체 동작.
- **공통**: Tab만으로 모든 버튼 도달, Esc로 모든 오버레이 닫기, 포커스가 사라지지 않음, 200%에서 내용 손실 없음, 색만으로 구분하는 정보 없음.

이 제안은 `docs/feedback-2026-11-03.md`의 "나중 작업"에 있던 접근성 묶음(키보드 조작, 시트 포커스, 포커스 링, 라이트 모드 대비, 키보드로 여는 우클릭 메뉴)을 흡수한다. 범위가 정해지면 그 문서의 항목도 함께 맞추는 것이 좋다.

## 8. 구조 보강 · 접근성 보강 계획 (제안)

> 7절의 접근성 항목을 기능마다 덧대지 않기 위한 계획이다. "구조"와 "접근성"을 1:1로 맞추지 않고 두 갈래를 따로 세운 뒤, 만나는 지점을 세 곳으로 좁혀 보는 제안이다. 확정 전 제안이다.

### 8-1. 지금 구조 진단

강점은 있다. `app.js` 안에 주제별 구역 주석이 있고, 상태 객체가 하나이며, 이벤트는 컨테이너 위임을 쓴다. 행 상태 계산(`rowState`)처럼 한곳에 모인 모델도 있다. i18n 카탈로그와 `esc()`도 있다.

문제는 "미약하게 설계됐다"기보다 **경계가 아직 없다**에 가깝다. 접근성을 덧대면 스파게티가 되기 쉬운 지점은 이렇다.

1. **한 파일 2,000줄 가까운 IIFE** — 의존 관계가 암묵적이고 단위 테스트 이음매가 없다.
2. **동작 모델이 없다** — 삭제·이름 변경·복사·열기·다시 시도·유료로 이어서가 스와이프 HTML, 행 버튼, 우클릭 메뉴에 각각 따로 있다. 키보드 경로는 아예 없다. 한 곳을 고치면 다른 곳이 어긋난다.
3. **`innerHTML` 통째 교체** — 행을 다시 그릴 때 포커스와 접근성 상태가 사라진다. 지금 렌더 방식 그대로 행에 포커스를 주면 키보드 조작이 깨진다.
4. **포커스·알림·단축키·대화상자가 기능마다 흩어져 있다** — 접근성 항목을 기능별로 붙이면 규칙이 갈라진다.
5. **렌더 호출이 수동** — `renderItems`·`renderPane`·`renderKeys`를 잊으면 접근성 상태도 함께 낡는다.
6. **화면 테스트가 없다** — `frontend/embed_test.go`는 파일 존재만 본다.

이 글을 쓴 사람은 이 규모에서 프레임워크를 넣기보다 **이음매를 만드는 쪽**이 비용이 낮다고 봤다. 반대 판단도 가능하고, 그 판단은 시니어에게 맡긴다.

### 8-2. 두 갈래

- **구조 보강**: 모듈 경계, 상태 흐름, 동작 모델, 렌더 방식.
- **접근성 보강**: 포커스, 알림, 키맵, 대화상자, 목록 탐색, 메뉴.
- 두 갈래를 1:1로 맞출 필요는 없다. 이 글에서는 두 갈래가 만나는 지점을 8-4의 세 곳으로 좁혀 봤다. 구조를 먼저 손보든 접근성을 먼저 손보든, 서로를 기다리지 않아도 되게 하려는 것이다.

### 8-3. 구조 후보 (빌드 단계 없이)

지금까지의 스타일(빌드 단계 없는 순수 파일)을 이어 가는 한 가지 형태다. Wails 자산 서버가 `.js`·`.mjs`를 `text/javascript`로 제공하므로 네이티브 ES 모듈을 쓸 수 있다. 이 구조를 강제할 생각은 아니고, 경계를 잡는 예시로 적었다.

```text
frontend/dist/
  index.html          <script type="module" src="main.js">
  main.js             부트스트랩: 기능 조립
  core/
    dom.js            $, esc, 이벤트 위임 helper
    store.js          상태 + subscribe (30줄 수준)
    i18n.js           t, applyStrings
    backend.js        call, errorText, 이벤트 구독
    platform.js       IS_MAC/IS_WINDOWS, 수정자 키 표기
  a11y/
    focus.js          save/restore, trap, focusable
    announcer.js      polite/assertive 라이브 영역
    keymap.js         범위별 단축키, 입력 중 무시
    dialog.js         시트·모달 열기/닫기/가두기/복귀
    listbox.js        activedescendant 목록 탐색
    menu.js           메뉴 로빙 포커스·Esc·복귀
  features/
    actions.js        동작 목록 (한 곳)
    items.js          목록 렌더·선택
    pane.js           전사본 칸
    keys.js           키 목록·설정
    pdf.js            PDF 선택
    toolbar.js        모드·추가·칸 토글·키 선택
    toast.js          토스트·실행 취소
  i18n/ko.json
```

한 가지 방향 예시는 `features → a11y → core`다. `core`가 기능을 모르게 두고, `features`끼리는 `actions`·`store`로 대화하면 결합이 줄어든다. 강제 규칙은 아니고, 시니어가 더 나은 경계를 그리면 그쪽을 따른다.

### 8-4. 두 갈래가 만나는 세 지점

1. **동작을 한곳에 모으면 좋다.** 스와이프, 행 버튼, 우클릭 메뉴, 키보드가 같은 설명을 보고 그리게 하는 방식이다. 접근성의 "모든 동작에 키보드 경로"가 체크리스트가 아니라 구조가 된다.

   ```js
   // features/actions.js
   const ACTIONS = {
     open:   { label: "action.open",   when: isDone,     run: (id) => call("OpenOutput", id) },
     copy:   { label: "action.copy",   when: isDone,     run: (id) => call("CopyOutput", id) },
     rename: { label: "action.rename", when: isFinished, run: startRename },
     delete: { label: "action.delete", when: always,     run: removeWithUndo, danger: true },
     // ...
   };
   export function available(item) { /* 표시 순서·가능 여부 */ }
   export function run(id, item) { /* 실행 */ }
   ```

2. **상호작용 요소에 역할·이름·상태를 함께 붙이는 편이 좋다.** `dom.js`에 `button({label, pressed})`, `row({selected})` 같은 작은 헬퍼를 두거나 템플릿 규칙을 문서화한다. 아이콘 버튼을 새로 넣을 때 `aria-label`을 빠뜨릴 수 없게 만드는 것이 목적이다.

3. **상태 변화가 한 경로를 지나면 렌더와 알림을 함께 부를 수 있다.** `store.subscribe`에서 화면 렌더와 `announcer.announce`를 연결하는 식이다. 상태 문구를 바꾸는 곳과 읽어 주는 곳이 갈라지지 않는다.

### 8-5. 접근성 기반 계층이 하는 일

| 모듈 | 책임 | 없으면 생기는 일 |
|---|---|---|
| `focus.js` | 시트 열기 전 포커스 저장, 닫을 때 복귀, Tab 가두기 | 시트를 닫아도 포커스가 사라지고, 기능마다 다른 처리를 하게 된다 |
| `announcer.js` | `#sr-status`(polite)·`#sr-alert`(assertive) 두 영역, 중복·폭주 억제 | `aria-live`를 콘텐츠 컨테이너에 붙이게 된다(지금 `#pane`) |
| `keymap.js` | 범위(전역·목록·대화상자)별 키, 입력 중 무시, 플랫폼 표기 | keydown 리스너가 기능마다 늘고 단축키가 충돌한다 |
| `dialog.js` | `role=dialog`, `aria-modal`, `inert` 배경, Esc, 첫 포커스 | 시트마다 다른 모달 구현 |
| `listbox.js` | `aria-activedescendant`, ↑↓·Home/End·Page, 선택 | 행을 다시 그릴 때 포커스가 사라진다 |
| `menu.js` | 로빙 포커스, 방향키, Esc, 포커스 복귀 | 우클릭은 되는데 키보드로는 못 연다 |

목록은 **`aria-activedescendant` 방식**을 이 글에서는 먼저 떠올렸다. 지금처럼 행 내용을 `innerHTML`로 갈아끼워도 DOM 포커스는 목록 컨테이너에 남아 있어 렌더 방식을 크게 바꾸지 않아도 된다. 행이 포커스를 직접 가지는 로빙 탭인덱스 방식은 렌더 교체 때마다 포커스를 복원해야 해서 지금 구조와 충돌할 수 있다. 어느 쪽이 나은지는 구현자 판단이다.

### 8-6. 마이그레이션 순서 후보 (한 번에 갈아엎지 않는다)

0. **기준선**: 지금 동작을 적은 수동 스모크 목록(드롭·검색·여닫기·시트·취소·삭제·이름 변경)을 만든다. 코드는 바꾸지 않는다.
1. **기반 추출**: `i18n`·`backend`·`dom`·`platform`을 `core/`로 옮기고 `app.js`가 import한다. 동작 변화 없음.
2. **접근성 기반 먼저**: `announcer`·`focus`·`dialog`를 넣고 토스트·시트·`#pane` 라이브 영역을 옮긴다. 렌더 개편과 분리한다.
3. **동작 모델**: `actions.js`를 만들고 스와이프·행 버튼·우클릭 메뉴를 여기서 그리게 한다. 이때 키보드 경로도 같이 생긴다.
4. **목록 기반**: `listbox.js`로 행 선택·탐색을 옮긴다. 행에 포커스가 없어도 되는 구조라 3번 뒤가 안전하다.
5. **기능 분리**: `pane` → `keys` → `pdf` → `toolbar` → `toast` 순으로 하나씩 `features/`로 꺼낸다. 한 번에 하나, 커밋 하나.
6. **`main.js`**: 빈 껍데기가 된 IIFE를 지우고 부트스트랩으로 바꾼다.
7. **테스트**: 모듈이 생길 때마다 순수 함수 테스트를 붙인다.

각 단계가 그 자체로 실행·배포 가능하면 좋다. 리팩터링과 기능 추가를 한 커밋에 섞지 않으면 되돌리기 쉽다. 이 순서도 후보이고, 시니어가 다시 짜는 것을 전제한다.

### 8-7. 기존 구조가 더 약할 때의 원칙

- **Strangler**: 새 모듈이 기존 함수를 감싸고, 기존 호출부를 조금씩 새 모듈로 옮긴다. 다 옮긴 뒤 옛 경로를 지운다.
- **순수 함수부터**: `rowState`, `actions.available`, 키맵 표, 날짜·비용 문구처럼 DOM이 없는 곳을 먼저 꺼낸다.
- **동작을 고정한 뒤 이동**: 0번 스모크 목록과 플랫폼별 확인 없이 구조를 옮기지 않는 편이 안전하다.
- **얽힌 기능은 나중에**: 스와이프+행+실행 취소처럼 강하게 얽힌 곳은 마지막. 시트·토스트처럼 경계가 선명한 곳부터.
- **프레임워크 도입**: 지금 규모(화면 3개, 목록 하나)에서는 빌드 단계와 의존성을 늘리는 비용이 이득보다 클 수도 있다. 다만 이 판단은 이 문서에서 정하지 않고 시니어에게 맡긴다.

### 8-8. 테스트·관리

- **순수 모듈**: `node --test`로 `actions`, `rowState`, `keymap`, 날짜·비용 문구를 테스트하는 안이 있다. Node는 테스트에만 쓰는 쪽이 가볍다. 제품 빌드에 넣을지는 별도 판단이다. CI는 Go CI를 만들 때 `setup-node`를 함께 두거나, 처음에는 로컬 명령으로 시작할 수 있다.
- **DOM·OS 동작**: 7-7의 수동 체크리스트. VoiceOver·Narrator·고대비·확대는 자동화보다 실기 확인이 정확하다.
- **문서**: `docs/development.md`의 문서 지도에 `docs/frontend-architecture.md`(가칭)를 추가하는 안이 있다. 계층 지도·의존 방향·"새 화면 요소 체크리스트"를 두는 형태다.
- **규칙**: 새 상호작용은 ① `actions.js`에 등록 ② 이름·역할·상태 선언 ③ 키보드 경로 ④ 포커스/알림 확인 ⑤ macOS·Windows 확인. 이 다섯 줄을 체크리스트로 두면 빠뜨리기 어렵다.
- **정적 검사(선택)**: `go test`에서 `frontend/dist`의 금지 패턴(콘텐츠 컨테이너의 `aria-live`, `tabindex` 없는 클릭 가능 요소)을 검사할 수 있지만 과하면 유지비가 크다. 자동 검사는 axe-core를 개발 중에 돌리는 정도가 현실적이어 보인다.

### 8-9. 정할 것

- 프런트를 지금 분리할지, 접근성에 필요한 기반(`announcer`·`focus`·`dialog`·`actions`)만 먼저 넣고 기능 분리는 릴리스 뒤로 미룰지.
- `actions.js`를 어디까지 옮길지: 행 동작만 vs 키 목록 동작까지.
- `node --test`를 개발 도구로 들일지, 수동 확인만 할지.
- `docs/frontend-architecture.md`를 새로 만들지, `development.md`에 절을 늘릴지.
- 목록 포커스 방식: `aria-activedescendant` vs 로빙 탭인덱스.

이 목록도 선택지를 좁히기 위한 것이 아니다. 시니어가 다시 정하는 것이 좋고, 이 문서는 그 판단에 필요한 배경만 남긴다.
